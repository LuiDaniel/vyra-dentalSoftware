Minutos 0–3

1. Mapa general: qué es y cómo está armada

Vyra es una aplicación de escritorio (no web) en Java 21 + JavaFX para un consultorio dental: pacientes, agenda, historia clínica, odontograma, tratamientos y pagos. Guarda todo en un archivo SQLite (vyra.db). Tiene tres roles —Administrador, Recepción, Odontólogo— y cada uno ve pantallas distintas.

La idea central es una arquitectura en capas estrictas: cada capa solo habla con la de abajo.

Por qué importa (para explicarlo en una frase)

“Si mañana cambiamos SQLite por otra base, solo se reescriben los DAO. Si cambiamos el diseño, solo se tocan FXML y CSS. Las reglas del negocio viven en un solo lugar: los Service.”

“Es una app de escritorio en Java con tres capas: pantallas, reglas de negocio y base de datos. Cada rol ve solo lo suyo.” Muestra: inicia sesión como recepcion y luego como msalinas (los que creaste en la preparación); el menú de la izquierda cambia.

Plugins de Maven: maven-compiler-plugin (compila con Java 21 y Lombok), maven-surefire-plugin (ejecuta las pruebas con una base en memoria, para no tocar vyra.db) y javafx-maven-plugin (lo que hace funcionar mvn javafx:run).

Los módulos de Java (module-info.java)

El proyecto usa el sistema de módulos de Java: un archivo que dice qué librerías necesita (requires javafx.controls, requires java.sql…) y qué paquetes abre para que otros puedan leerlos. Dos opens importan: controller y ui se abren a javafx.fxml, porque el cargador de FXML crea los controladores “por reflexión”; y model se abre a javafx.base (tablas) y a hibernate.validator (lee las anotaciones). Si falta uno, la app falla al abrir la pantalla.

Qué NO se usó (y por qué lo preguntarán)

  • Sin framework web ni servidor: es de escritorio, un solo equipo.
  • Sin ORM (Hibernate/JPA): el SQL se escribe a mano en los DAO. Hibernate aquí solo se usa para validar, no para guardar.
  • Sin Spring: los servicios se crean a mano en una clase fábrica (Servicios).
“Usamos solo lo necesario: JavaFX para la interfaz, SQLite como base embebida, Jakarta Validation para validar y OpenPDF para los PDF.” Muestra: abre pom.xml y recorre el bloque <dependencies>.
Minutos 8–13

3. Arranque y base de datos

Qué pasa desde que se abre la app hasta que ves el login

  • ConexionBD mantiene una sola conexión compartida (por eso los DAO nunca la cierran). La primera vez que se pide, activa las claves foráneas (PRAGMA foreign_keys = ON) y ejecuta schema.sql, que usa CREATE TABLE IF NOT EXISTS: si el archivo no existe, se crea con todas las tablas.
  • DatosIniciales crea el usuario admin solo si no hay ningún usuario. Su contraseña se guarda con HashUtil (PBKDF2 con sal), nunca en texto plano.

Las 9 tablas y cómo se relacionan

“La base se crea sola la primera vez. Nada del saldo se guarda a mano: se calcula, así nunca queda desactualizado.” Muestra: en la carpeta del proyecto aparece vyra.db tras abrir la app.

4. Un caso completo de punta a punta: “Agendar una cita”

La mejor forma de entender las capas es seguir un clic. Este es el recorrido cuando recepción pulsa Agendar cita:

Qué hace cada capa en ese recorrido

Vista

AgendaView.fxml

Dibuja el formulario y los botones. Cada botón dice onAction="#guardarCita": así el FXML sabe qué método del controlador ejecutar. Los campos con fx:id se inyectan en variables @FXML.

Controller

AgendaController

Lee lo que escribió el usuario, construye un objeto Cita, llama al Service y atrapa los errores para mostrarlos junto al campo. No decide reglas: solo conecta pantalla y Service. Pide su Service a Servicios.citas().

Service

CitaService

Aquí viven las reglas: horario de 08:00 a 20:00 (RN-05), sin cruces (RN-06), sin fechas pasadas (RN-08), y qué rol puede hacer qué. Recibe su DAO por constructor, así en las pruebas se le pasa uno “falso” en memoria.

DAO

CitaDAO → CitaDAOSqlite

CitaDAO es la interfaz (el contrato: crear, buscarPorId, listarPorFecha…). CitaDAOSqlite la implementa con SQL. Siempre PreparedStatement con ?, por seguridad contra inyección SQL.

Model

Cita, Paciente, EstadoCita…

Clases simples con datos (Lombok genera getters/setters) y las anotaciones de validación. Los enums (EstadoCita, Rol…) tienen su texto para mostrar (getEtiqueta()).

Util

Validador, Formatos…

Validador ejecuta las anotaciones y lanza ValidacionException con un mensaje por campo. Formatos da las fechas en español y el dinero como S/ 1,250.00.

Dos piezas “transversales” que conviene dominar

  • Servicios (fábrica): crea cada Service una sola vez con sus DAO de SQLite. Es el único lugar donde se “enchufan” las capas. Ej.: new CitaService(new CitaDAOSqlite()).
  • Sesion (singleton): guarda quién inició sesión y su rol. Los Service la consultan (Sesion.get().tieneRol(Rol.ADMIN)) para decidir si permiten una acción. Es la “defensa en profundidad”: aunque el menú oculte una pantalla, el Service también verifica.

¿Y los errores?

Hay dos tipos y ambos terminan como texto rojo junto al campo: ValidacionException (un campo mal escrito, viene de las anotaciones del modelo) y ReglaNegocioException (una regla del negocio rota, viene del Service, con el mensaje ya listo para el usuario).

“La pantalla nunca decide si una cita es válida: eso lo hace el servicio. Por eso las reglas se prueban sin abrir ninguna ventana — tenemos 185 pruebas automáticas.” Muestra: en la agenda, intenta agendar a la misma hora del mismo odontólogo y enseña el aviso de cruce con los horarios libres.

La navegación: cómo se pasa de una pantalla a otra

  1. MainView.fxml es el marco: menú lateral + barra superior + un área central.
  2. MainController construye el menú leyendo el enum Pantalla, que dice, para cada pantalla, su título, ícono, archivo FXML y qué roles la ven. Por eso un rol no ve lo que no le toca.
  3. Al hacer clic, navegar(Pantalla) carga el FXML con FXMLLoader y lo pone en el área central.
  4. Si una pantalla necesita un dato (ej. “abrir el odontograma de este paciente”), su controlador implementa RecibeParametro y recibe el objeto: navegar(Pantalla.ODONTOGRAMA, paciente).
  5. Si una pantalla tiene cambios sin guardar (el odontograma), implementa ConfirmaSalida y el marco le pregunta antes de dejarte salir.

Preguntas que te pueden hacer

¿Dónde se guardan los datos?
En un archivo SQLite, vyra.db, en la carpeta donde corre la app (en la versión empaquetada, en %APPDATA%\Vyra). No hay servidor.
¿Las contraseñas están seguras?
Se guardan como hash PBKDF2 con sal (HashUtil), nunca en texto plano. El login no dice cuál dato falló.
¿Qué evita que dos citas se crucen?
El CitaService consulta al DAO si hay una cita del mismo profesional que se traslape, antes de guardar. La pantalla solo muestra el resultado.
¿Por qué hay DAO “en memoria” y DAO “Sqlite”?
Para probar las reglas del negocio sin base de datos real: las pruebas usan los de memoria (o SQLite en memoria) y corren en segundos.
¿Qué pasa si recepción intenta ver el odontograma?
No lo ve en el menú, y aunque llegara, el OdontogramaService lanza “sin permiso”: se verifica en las dos capas.
¿Se puede borrar una cita, un pago o una entrada de historia?
No. Las citas se cancelan, la historia y el odontograma solo agregan filas nuevas, y los usuarios se desactivan. Así queda un historial confiable.
¿Cómo se prueba?
185 pruebas JUnit (mvn test), sobre todo de los Service y los DAO, con una base en memoria.
¿Cómo se entrega?
scripts/empaquetar.ps1 genera una carpeta con Vyra.exe usando jpackage; incluye su propio Java.
